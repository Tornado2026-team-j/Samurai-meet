# 機能仕様：本人確認

## 1. 対象

ユーザーのプロフィールに本人確認状態を表示し、交流相手が安心材料として利用できるようにします。

対応要件：FR-005、C-002、C-005

## 2. 状態

```text
unverified -> pending -> verified
                         └-> expired
pending -> rejected -> pending（再申請可否は要確認）
```

| 状態 | ユーザー表示 | 募集・マッチング |
| --- | --- | --- |
| `unverified` | 未確認 | 通常利用可否は要決定 |
| `pending` | 審査中 | バッジは付けない |
| `verified` | 本人確認済み | 絞り込み対象 |
| `rejected` | 確認できませんでした | 再申請方針に従う |
| `expired` | 再確認が必要 | 要件により制限 |

## 3. 処理フロー

1. ユーザーが本人確認の説明と利用目的を確認する。
2. 外部本人確認プロバイダーまたはサービス画面で申請する。
3. Go API が申請状態を `pending` にする。
4. プロバイダーの検証結果を Webhook または管理画面から受け取る。
5. 署名・送信元を検証して `verified`、`rejected`、`expired` を更新する。
6. 他ユーザーへは状態バッジだけを表示する。

## 4. 実装分担

| 処理 | 言語 / 場所 |
| --- | --- |
| 説明・同意・申請 UI | TypeScript / TSX |
| プロバイダー SDK 呼び出し | TypeScript またはプロバイダー指定 SDK |
| Webhook 検証・状態遷移 | Go |
| 対象ユーザーへのバッジ返却 | Go |
| 状態・参照 ID・日時の保存 | PostgreSQL / SQL |

## 5. API / DB

- `POST /me/verification`
- `GET /me`
- 運営用 `POST /admin/identity-verifications/{id}/decision`（管理者 API として別認可）
- テーブル：`identity_verifications`、`profiles.identity_status`、`audit_logs`

証明書類を自前 DB に保存する場合は、保存期間、暗号化、アクセス監査、削除を別途設計します。MVP ではプロバイダーに保持させ、サービス側は参照 ID と状態だけを保存する案を優先します。

## 6. 受け入れ条件

- 申請前・審査中・確認済み・否認の状態が画面で区別できる。
- 審査結果が正規の Webhook または管理操作からのみ更新される。
- 他ユーザーが本人確認書類の画像を取得できない。
- `verified` のユーザーを検索条件で絞り込める。
- 審査状態変更が監査ログに残る。

## 7. 要確認

- 本人確認プロバイダーと国・年齢対応。
- 本人確認の必須タイミング。
- 再申請、期限、否認理由、問い合わせ対応。
- 本人確認済みでも安全を保証しないことの表示。
