# 審査員向けリモートテストキット

最終更新: 2026-09-04
状態: 準備手順。ハッカソン発表では、Demo専用環境で通常フローを再利用する発表用MVPを第一候補にする。

このキットは、ハッカソン発表時に審査員が自分の端末または配布端末で Samurai Meet を短時間触れるようにするための運用資料です。実装状態の正本は [実装状態の境界](../ai/system/current-status.md)、デモアカウントの設計は [Demoアカウント仕様](../features/demo-account.md) を参照してください。

## 1. 当日のゴール

審査員が10分から15分で次を確認できる状態にします。

- 外国人側が「いま近くで一緒に行きたいこと」を募集できる。
- 日本人側が募集を検索し、応募できる。
- 募集者が応募を承認し、マッチが成立する。
- アプリ内通知とチャット画面へ遷移できる。
- チャット送信前Moderation、暗号化RESTチャット、画像添付など、現行実装済みの境界を説明できる。

発表用MVPでは、審査用ビルドの「デモを体験する」から24時間の一時アカウントを発行します。
Demo専用APIへ分離する構成と、明示的な本番APIフラグで有効化する構成のどちらでも、
プロフィール、募集、応募、承認、チャットは通常画面と通常APIフローを再利用します。

## 2. 配布物

審査員へ渡すものは、1つの短い案内にまとめます。秘密値はこのリポジトリ、スライド、録画、公開チャットへ書きません。

| 項目 | 内容 | 渡し方 |
| --- | --- | --- |
| アプリ導線 | TestFlight / Ad Hoc / Android APK / Expo Goのいずれか | QRコードまたは短縮URL |
| API接続先 | 審査用APIのBase URL | 案内には環境名だけを書く。完全なURLは必要な人だけに渡す |
| Demo入口 | 「デモを体験する」ボタン | 審査用ビルドだけで表示 |
| 予備テストアカウント | 募集者A、応募者Bの2組以上 | Demo入口が使えない場合だけ非公開チャンネルで渡す |
| 体験シナリオ | 10分版と15分版 | この文書の「審査員向け操作カード」を転記 |
| サポート連絡先 | 当日の担当者、復旧手順 | 発表用チャットまたは会場連絡先 |

Expo Goの公開URLやEAS UpdateはExpoログインが必要になるため、ログインなしでリモート配布する場合は Android APK または iOS TestFlight / Ad Hoc を優先します。同一LANの `bun run start:offline` は開発確認用であり、リモート審査の配布手段にはしません。

## 3. 推奨構成

### 3.1 発表用Demo MVP

発表用MVPは、審査用ビルドに「デモを体験する」を表示し、`POST /api/v1/auth/demo/start` で24時間の `demo` アカウントを発行する方式です。

この方式を審査本番で使う条件は次の通りです。

- Demo APIを分離する場合は、Demo DB、署名鍵、ストレージ、ログ領域も分離されている。
- 現在の本番APIで動かす場合は、`DEMO_ACCOUNT_ENABLED=true`をAPI側で明示し、
  `account_type`・期限・Demo同士限定の全API境界を確認する。
- `EXPO_PUBLIC_DEMO_ACCOUNT_ENABLED=true`をクライアント側で明示する。
- Googleログインを閉じる審査ビルドでは`GOOGLE_LOGIN_ENABLED=false`と
  `EXPO_PUBLIC_GOOGLE_LOGIN_ENABLED=false`を設定する。通常ログインと併用する場合は両方trueにする。
- 本番APIのDemoフラグは既定falseとし、発表時だけ明示的に有効化する。
- Demo同士の募集、応募、承認、チャットが二端末E2Eで成功している。
- 審査員がGoogleログインを使わず、Demo入口から開始する案内になっている。

このMVPは、Demo専用鍵 `demo-keyb-v1` とDemo専用チャット鍵 `demo-chat-v1` までは実装しません。Demo専用環境で通常のKey-A / Key-B / Recovery Phrase / chat DEKフローを再利用するため、本番アカウント向け機能として説明しません。

### 3.2 当日のfallback

Demo入口、審査用API、端末配布のいずれかに問題がある場合は、通常アカウントを使った「審査用テストアカウント方式」へ切り戻します。審査員の個人アカウントは使わず、運営が準備したテスト専用アカウントだけを使います。

- 募集者A: 外国人側モード。募集作成と応募承認を担当。
- 応募者B: 日本人側モード。検索、応募、チャット開始を担当。
- 予備アカウント: ログイン失敗、Passkey登録失敗、端末取り違えに備えて2組以上。
- テストデータ: 自宅、実在の個人情報、実際の予定を含めない。

アカウントID、Refresh Token、Recovery Phrase、Key B、Passkey情報は記録・共有しません。スクリーンショットを残す場合も、アカウント識別子は末尾4文字などにマスクします。

## 4. 運営準備チェックリスト

### 4.1 ビルドと接続先

- 審査に使うコミットを固定し、`git rev-parse HEAD` を記録する。
- `git status --short --untracked-files=all` を確認し、`backend/` と `frontend/` の意図しない差分をビルドに混ぜない。
- backendは [backend/.env.demo.example](../../backend/.env.demo.example) を元に、Demo専用DB、署名鍵、ストレージへ向ける。
- frontendは [frontend/.env.demo.example](../../frontend/.env.demo.example) を元に、Demo APIへ向ける。
- 審査ビルドの `EXPO_PUBLIC_API_BASE_URL` が審査用APIを指していることを確認する。
- 審査ビルドの `EXPO_PUBLIC_DEMO_ACCOUNT_ENABLED=true` を確認する。
- 審査ビルドの `EXPO_PUBLIC_GOOGLE_LOGIN_ENABLED=false` を確認する。
- iPhone向けは `127.0.0.1` や `localhost` を埋め込まない。
- Android APKまたはiOS TestFlight / Ad Hocの導線を、審査開始前に別端末で開けることを確認する。

### 4.2 APIとデータ

- `/healthz`、`/readyz`、`/api/v1/healthz`、`/api/v1/readyz` が成功する。
- 審査用APIで `DEMO_ACCOUNT_ENABLED=true` が有効になっている。
- 審査用APIで `GOOGLE_LOGIN_ENABLED=false` が有効になっている。
- `APP_ENV=production` のAPIでは、発表時だけ `DEMO_ACCOUNT_ENABLED=true` を明示し、
  通常運用へ戻すときは `false` に戻す。
- DBは審査用データだけを扱う。通常本番利用者へ通知が飛ぶ環境を使わない。
- `GEMINI_API_KEY` は募集分類に使うサーバー側だけへ設定する。
- `OPENAI_API_KEY` はチャット本文Moderation用に設定する。未設定時は送信がfail-closedになる。
- `CHAT_MODERATION_DEV_FREE_MODE=true` は実データを使わない一時確認に限定する。
- 画像添付を見せる場合は `IMAGE_STORAGE_DIR` とアップロード上限を確認する。

### 4.3 Demo / テストアカウント

- 審査前に「デモを体験する」から募集者A、応募者Bを作成する。
- A/Bそれぞれでプロフィール設定、利用モード設定、Recovery Phrase確認まで完了する。
- テスト用プロフィールには審査で見せたい価値が伝わる自己紹介を入れる。
- 募集日は現在のJSTより未来にする。
- Demo入口が失敗した場合に備え、予備の通常テストアカウントA/Bも用意する。
- テスト後にセッション失効、アカウント削除、DB清掃を実施する担当者を決める。

### 4.4 事前リハーサル

審査の前に、運営の端末2台で同じシナリオを1回通します。

- Aが募集を作成して公開できる。
- Bが検索結果から募集を見つけ、応募できる。
- Aが応募を承認できる。
- A/B双方でアプリ内通知または一覧更新から状態変化を確認できる。
- チャットで短い本文を送受信できる。
- エラー時の表示、再試行、手動更新の案内を説明できる。

## 5. 審査員向け操作カード

この章は、そのまま審査員へ渡せる短い案内です。

### 5.1 10分版

1. アプリを開き、「デモを体験する」を押します。
2. 募集者側の端末で「募集を作成」を開き、例文を入力します。
3. 確認画面でカテゴリとキーワードを選び、「公開する」を押します。
4. 応募者側の端末で日本人側ホームを開き、募集を検索します。
5. 募集詳細から応募します。
6. 募集者側で応募を開き、承認します。
7. チャット一覧または通知からチャットを開き、短いメッセージを送ります。

入力例:

```text
大阪駅の近くで、旅行中に入りやすいランチのお店を一緒に探したいです。
```

### 5.2 15分版

10分版に加えて、次も確認します。

- 表示言語を日本語から英語へ切り替え、利用モードが勝手に変わらないことを見る。
- 応募前の状態で、応募者側から応募を取り下げる。
- チャットで送信前Moderationが走ることを説明する。
- 余裕があれば画像添付を行う。失敗時は実機未確認項目として扱い、テキストチャットへ戻る。
- 通報・ブロックの入口を確認する。

## 6. 審査員へ事前に伝える既知の境界

ハッカソン審査では、未実装と実装済みを正直に分けて説明します。

| 項目 | 当日の説明 |
| --- | --- |
| Demoアカウント | 発表用MVP。Demo専用環境で24時間アカウントを発行し、鍵とチャットは通常フローを再利用する |
| OSプッシュ通知 | 未実装。現在はアプリ内通知一覧と未読管理 |
| WebTransport | バックエンドは実装済み。Expo GoではREST同期、native bridgeの実機E2Eは未完了 |
| チャット暗号 | RESTの暗号文送信、履歴、画像添付は実装済み。Moderationと翻訳は暗号化前平文の明示例外 |
| 本人確認 | 仕様と画面境界はあるが、運営審査フローは未完了 |
| 実機E2E | 自動テスト成功と実機PASSは分けて記録する |

## 7. トラブル時の切り戻し

審査中に詰まったら、原因調査より体験継続を優先します。

| 症状 | 当日の対応 |
| --- | --- |
| インストールできない | 予備端末または録画デモへ切り替える |
| ログインできない | 予備アカウントへ切り替える。個人アカウントは使わない |
| APIに繋がらない | `/readyz` とビルドのAPI接続先を運営が確認する |
| 募集が見つからない | 募集日時、利用モード、検索条件、位置情報許可を確認する |
| チャット送信が止まる | Moderation設定とネットワークを確認し、必要なら既に成立済みの予備matchを使う |
| 画像添付が失敗する | テキストチャットへ戻す。画像は実機未確認項目として扱う |

録画デモを併用する場合も、録画はfallbackであり、審査員が触れる導線の代替説明にしません。触れる導線が止まった場合の保険として準備します。

## 8. 当日案内テンプレート

```text
Samurai Meet リモート体験

1. 下のリンクからアプリを入れてください。
   iOS: <TestFlightまたはAd Hocリンク>
   Android: <APKリンク>

2. アプリを開いたら「デモを体験する」を押してください。
   個人のGoogleアカウントや実住所は使わないでください。

3. まずは10分版シナリオをお試しください。
   募集を作る人: A端末
   応募する人: B端末

4. 動かない場合は、画面名と時刻だけを教えてください。
   token、Recovery Phrase、Passkey、個人情報は送らないでください。
```

## 9. 終了後の片付け

- TestFlight / Ad Hoc / APKの公開範囲を閉じる。
- 審査用セッション、Refresh Token、Demoアカウント、予備テストアカウント、募集、match、chat、画像添付を削除する。
- ログにtoken、Recovery Phrase、Key B、本文、画像平文が出ていないことを確認する。
- 審査で実際に触れたビルド種別、API接続先、成功/失敗、未確認項目を記録する。
- 本番向けDemoアカウント方式へ移行する場合は、[Demoアカウント仕様](../features/demo-account.md) のリリースゲートを満たしてから一般配布へ使う。
